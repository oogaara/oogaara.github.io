Uma trilha para observar como uma aplicação recebe dados, toma decisões e devolve respostas. Comece pelo comportamento normal; depois compare cada entrada, método e contexto de execução.

NOTAS DE LABORATÓRIO. Conteúdo organizado a partir das suas anotações. Exemplos usam domínios e credenciais fictícios; as explicações adicionadas servem para dar contexto, corrigir sintaxe quando necessário e orientar a leitura.
FIELD NOTE

01 / Primeiro, entenda o fluxo

Busque pela documentação da API. Teste os métodos HTTP aceitos, os códigos de resposta, a autenticação e as diferenças entre usuário anônimo e autenticado. Registre a requisição original antes de alterar parâmetros.

Em GraphQL, a introspecção pode revelar tipos, campos e argumentos quando estiver habilitada. A consulta completa está nas notas originais; para uma primeira leitura, comece por __schema e queryType.

query { __schema { queryType { name } types { name } } }
A documentação e a introspecção são pontos de partida. Não conclua que uma rota é vulnerável apenas por estar exposta.
FIELD NOTE

02 / Descoberta de rotas e parâmetros

Podemos passar um arquivo para o ffuf para ele fazer os requests. Basta pegar a request, adicionar FUZZ onde queremos testar e comparar as respostas. Feroxbuster ajuda a descobrir diretórios e arquivos em aplicações de laboratório.

ffuf -request req.txt -w wordlist.txt
feroxbuster --url https://app.exemplo.test/ -w caminhos.txt -t 10 -C 400,500

Observe tamanho, status e tempo de resposta. Ajuste a taxa para não derrubar o serviço durante um teste autorizado.

FIELD NOTE

03 / Injeção de comandos

Os separadores &, &&, |, ||, ; e quebras de linha podem alterar a forma como um shell interpreta uma entrada. O contexto importa: aspas, filtros e a chamada real do programa mudam o resultado.

valor; id
valor && whoami
valor | wc -c
Use comandos de observação em laboratório. Ao encontrar o ponto de entrada, documente o parâmetro e recomende execução sem shell, validação da entrada e privilégios mínimos.
FIELD NOTE

04 / SQL Injection

As notas cobrem descoberta por união, leitura do esquema e automação com sqlmap. A sequência útil é confirmar a diferença na resposta, identificar o banco, mapear tabelas e colunas relevantes e registrar o impacto com o mínimo de dados necessário.

sqlmap -r req.txt --technique=BEUSTQ

B = boolean-based blind; E = error-based; U = UNION; S = stacked queries; T = time-based; Q = inline queries. A opção correta do sqlmap é --technique no singular.

As notas também mostram information_schema, group_concat e LOAD_FILE. Trate leitura de arquivos como impacto possível, dependente dos privilégios do banco e da configuração do servidor.

Defesa: consultas parametrizadas, privilégios mínimos para a conta do banco e mensagens de erro sem detalhes internos.
FIELD NOTE

05 / NoSQL Injection

Em aplicações que constroem consultas a partir de objetos recebidos, operadores como $regex e $ne podem mudar a lógica esperada. As notas incluem testes de condições verdadeiras/falsas e referência ao NoSQLmap.

{"username":{"$regex":"admin.*"},"password":{"$ne":""}}

Compare respostas e valide como o servidor transforma os tipos recebidos. Use esquemas de entrada que impeçam operadores inesperados.

FIELD NOTE

06 / SSTI e execução no servidor

Server Side Template Injection acontece quando uma entrada é interpretada como expressão de template. As notas registram marcadores de diferentes mecanismos. Um teste inicial simples é verificar se uma expressão aritmética é avaliada.

{{7*7}}
${7*7}
{% 7 * 7 %}

Não misture sintaxes: cada engine tem regras próprias. Se houver avaliação, identifique a engine e os objetos disponíveis antes de concluir o impacto. Nunca renderize entrada não confiável como template.

Em Node.js, as anotações também mostram leitura de arquivo com fs e execução via child_process. Esses trechos são exemplos de impacto após uma falha de execução, não etapas de descoberta.

FIELD NOTE

07 / XSS, HTML e Markdown

As notas de XSS reúnem contextos HTML, atributo, URL, string JavaScript e Markdown. O mesmo texto não funciona em todos eles. Primeiro descubra onde a entrada aparece e qual codificação o navegador aplica.

<img src=x onerror=alert(1)>
<a href="javascript:alert(1)">teste</a>

O arquivo original também incluía exemplos de envio de cookies e credenciais. No guia público, o teste de conceito usa um efeito visível local. Para demonstrar impacto, descreva o alcance sem coletar dados reais.

Defesa: escape conforme o contexto de saída, sanitização de HTML/Markdown, CSP e cookies HttpOnly quando cabível.
FIELD NOTE

08 / JWT, CSRF e CORS

JWT

Uma das notas descreve a troca de alg por none em um laboratório com verificação defeituosa. O ponto final continua representando a assinatura vazia. Isso só funciona quando o servidor aceita indevidamente um token sem assinatura; a correção é fixar algoritmos permitidos no servidor e validar assinatura, emissor e audiência.

Há também referência ao modo 16500 do Hashcat para avaliar segredos JWT fracos em laboratório. Prefira chaves fortes e rotação controlada.

CSRF

O exemplo original envia um formulário de mudança de e-mail a partir de outra origem. Para revisar a proteção, verifique token anti-CSRF, cookies SameSite e confirmação da ação sensível.

CORS

As notas cobrem reflexão de Origin e origem null. Uma configuração permissiva com credenciais pode expor respostas a origens não confiáveis. Revise a lista de origens e o uso de Access-Control-Allow-Credentials.

FIELD NOTE

09 / Outras superfícies web

  • File Upload: validar tipo real, extensão, armazenamento e execução no servidor.
  • Path Traversal: investigar normalização de caminhos e acesso fora do diretório esperado.
  • HTTP Request Smuggling: divergência de parsing entre proxy e servidor.
  • Insecure Deserialization: objetos não confiáveis recriados com efeitos inesperados.
  • Prototype Pollution: chaves controladas que alteram protótipos JavaScript.
  • Race Conditions: operações concorrentes que quebram invariantes de negócio.
  • Remote Code Execution: impacto de uma falha, não uma categoria única de entrada.
